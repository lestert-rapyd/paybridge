How to read this

Each specimen renders inside the app's real ancestor chain — .pane-left › .browser › .browser-body › .checkout — under the shipped tokens.css, main.css, cof.css. So the 470px card width, the warm paper, the accent and every inherited rule are the app's, not this page's. If a specimen looks wrong here it is wrong in the app.

Two liberties, both deliberate: ids are stripped (they carry no styling, and duplicating #acct-block nine times would be invalid), and the entrance-stagger classes .rise-* are kept, so the receipt specimens fade in once on load exactly as they do after a payment. Nothing here is interactive — a specimen is a still.

Keeping it honest. This page is hand-authored from the producing functions, so it can drift. Every specimen names its producer as file.js → fn(). Change a producer, change the specimen in the same commit — the same discipline DESIGN-SYSTEM.md already asks for when a primitive changes.

Drift is checkable, not just promised. The sample data is the app's own default identity, so every specimen the app can reach without firing a call is byte-comparable with it. From the app's console, walk the frames, capture outerHTML, then fetch() this page, parse it with DOMParser, and compare both sides normalised — strip id, data-*, autocomplete, type, readonly and whitespace. Eight components currently match exactly: both chooser states, the product grid, the Back rail, the guest strip, the pending strip, the account form and the frame actions.

Frame 1 — the account question

Two answers, in choice-card grammar (.bo-route). Each answer has a money consequence the SE narrates — an account can hold a card for later, a guest cannot — so the consequence sits on the card and nothing else explains it. Answering fires no call: the engine room shows its resting empty state.

The unanswered state is the one that matters. state.identityMode defaults to 'guest', so without the answered flag this frame would render an answer nobody gave.

Frame 2 — the account form

One field per row, in the request body's own order, so the eye tracks straight across from a field to the line it writes — focusing a field lights that JSON path in the engine room. The two actions sit on one plane: they are two answers to the same question, and the primary carries the gradient.

Length follows the vertical. The request body always carries all ten fields, so one cus_*** stays AFT-ready everywhere — but only a vertical whose real-world equivalent would ask shows the four KYC fields. The receipt

A receipt is something a shopper reads. The rows are set in the UI face, not mono, and are not click-to-copy: the old treatment made the end of a successful demo read as a debug dump. The ids the SE needs — payment, reference, customer — are one pane to the right, and the order number is derived from the same reference so they can still be tied together out loud.

08

Rules ratified here

Five amendments to DESIGN-SYSTEM.md that the frame map forced, and one question left open for whoever needs it first. Rules 1–5 are settled and recorded in the doc's §11.

  • A control may name its own parameter. It may not teach. Layer C stays embedded in the client UI, so the storefront legitimately carries the editable price tile, the FX bubble, Use test card, the strategy popover, the 3-D Secure checkbox and the dark config panel — and each may label itself with the real API key in mono. What comes off is the sentence: the paragraph explaining which call the parameter belongs to, the "updates the request →" pointer, "MIT charges run from the back office", "card details never touch this server". Those are the SE's punchlines, printed. Amends §1 and §6.
  • No progress token on the storefront. The step rail is Back only. The four beats are the SE's structure, not the shopper's, and a shop does not number its own pages. Nothing replaces the dropped "Step n of 4" — the store header on every frame is what keeps the sequence from reading as a wizard. Adds to §5.
  • Optimistic states are not labelled on the client surface. §8 law 5 asked every optimistic state to say "waiting for the confirmation webhook…". The webhook stays the source of truth — no optimistic success screens, no faked terminal state — but the label is engine-room vocabulary and belongs to the status pill and the Webhooks tab. The shipped processing screen already says "This only takes a moment — please don't close this page." and is better for it. Amends §8 law 5.
  • The receipt's value cell is UI face, sized above its label. 13.5px / 700 / --c-ink-2 against a 13px --c-ink-5 label. Not mono, not click-to-copy, no code element — the click-to-copy rules from that era are dead and come out with it. Amends §5.6.
  • The pending strip promises rather than reports. "Account not created yet" was the last piece of system voice on the storefront, and its · glyph was nearly invisible in a 20px disc. It now renders the same row as the created state — name, email, and "We'll save these details when you place your order." — with a + tick. The details in the form are exactly what gets saved, so saying so is both shopper-true and honest about the fact that no customer exists yet. It also gives the SE a free before/after: the identical row, one sub-line apart, on either side of POST /v1/customers. Adds to §5.8.
  • Open — a frozen field's fill on the toolkit's dark config panel. .acct-block.locked is defined against the warm client card only. The toolkit's own inputs live on --se-* near-black, where --c-soft-2 would be wrong. Nothing renders that combination today, so no rule was invented for it — the first surface that needs one should derive it from --se-surface-2 rather than reach for the client token.
